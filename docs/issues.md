## ISS-001: Spike ISA simulator fails to launch (missing libboost_regex.so.1.66.0)

- **Symptoms**: `spike --version` (and any invocation) exits immediately with
  `error while loading shared libraries: libboost_regex.so.1.66.0: cannot open shared object file: No such file or directory`.
- **Reproduction**: `module load spike/1.1.1 && spike --version` from any shell on this host.
- **Log location**: captured inline in `docs/development_log.jsonl` event E005; `ldd /edatools/opensrc/spike/1.1.1-dev/bin/spike` also reports `libboost_system.so.1.66.0 => not found`.
- **Diagnosed cause**: The prebuilt Spike binary at `/edatools/opensrc/spike/1.1.1-dev/bin/spike` was linked against Boost 1.66 shared libraries. A system-wide search (`find / -iname 'libboost_regex.so.1.66*'`) found no copy of that exact SONAME anywhere on the host; only newer Boost builds (1.72, 1.86) exist under vendor tool trees (Xilinx Vivado), which are not ABI-compatible drop-in replacements for a binary expecting 1.66.
- **Attempted fixes**: Searched for an alternate module providing the right Boost version; none exists. Did not attempt to symlink a mismatched-version `.so` onto the expected SONAME, since that risks silent ABI corruption in the comparator used for processor verification evidence — unacceptable for this project's integrity requirements.
- **Resolution**: Not fixed. Per claude_implementation_prompt.txt Section 6 contingency ("If unavailable within the deadline, implement a separate functional verification model from the specification, without reusing DUT logic, and record that limitation"), processor verification uses a hand-written Python RV32IM functional reference model (see `scripts/isa_reference_model.py`, docs/decisions.md D-002) instead of Spike.
- **Confirming rerun**: N/A (not fixed; fallback adopted instead).
- **Remaining limitation**: Comparisons are against an independently authored reference model, not against Spike/Sail. The reference model's own correctness is argued from the RISC-V ISA specification and covered by its own unit tests, but it has not been cross-checked against a second independent implementation.

- **Reproduction**: Call any `mcp__animas__*` tool after the Animas desktop app is confirmed running and its MCP endpoint answers `GET http://localhost:27500/mcp/sse` with `HTTP/1.1 200` (confirmed via `curl`).
- **Log location**: `/home/rmata/.var/app/com.mifraltech.animaseda/data/animas-eda/logs/animas.log` (JSON-lines) and the app's stdout/stderr log; the relevant line is a WARNING: `Failed to validate request: Received request before initialization was complete` at `session.py:383`, recurring on every subsequent attempt across multiple full restarts of the Animas desktop process.

## ISS-003: C++ function-local `static` TFLM objects silently failed to construct on RV32 firmware

- **Symptoms**: `interpreter.AllocateTensors()` failed on its first and only call with `MicroAllocator: Model allocation started before finishing previously allocated model` / `Failed starting model allocation.`, even though the allocator's constructor unconditionally initializes `model_is_allocating_ = false`. Identical C++ source compiled and ran correctly on the native x86 build.
- **Reproduction**: `sw/app/main_firmware.cc` (original draft) declared `static tflite::MicroMutableOpResolver<2> resolver;` and `static tflite::MicroInterpreter interpreter(...)` as function-local statics inside `main()`; run the firmware on RTL via Animas with `+MEMFILE=build/firmware/firmware.hex`.
- **Log location**: `output/zsim.log`; the `MMIO_TX` byte stream decodes to the exact error text above (captured via `DebugLog`); see docs/development_log.jsonl.
- **Diagnosed cause**: Function-local statics with non-trivial constructors use Itanium-ABI "guarded" dynamic initialization (a hidden guard-variable check executed every time control flow reaches the declaration). Diagnostic markers (`mmio_putc('1')` .. `('6')`, one after each construction step) confirmed control flow reached past the `interpreter` declaration while the object's observable internal state showed its constructor body never actually ran — pointing at the guarded-init codegen for this specific toolchain/ABI/target combination, not at reachability of the constructor function itself. Removing `-Wl,--gc-sections`/`-ffunction-sections`/`-fdata-sections` first (to rule out `.init_array`-pointed-to constructor functions being dead-code-eliminated) did not fix it, ruling that theory out.
- **Attempted fixes**: (1) Removed `-Wl,--gc-sections` and related flags from the firmware link — no change. (2) Moved `tensor_arena`, `resolver`, `model`, and `interpreter` to file (global) scope, in dependency order, so they are constructed unconditionally via this project's own `crt0.S` `.init_array` loop instead of the guarded-local-static mechanism.
- **Resolution**: Fix (2) resolved it. Confirmed by rerun: the `AllocateTensors()` failure no longer occurs; the firmware proceeds to real `Invoke()` execution (see ISS-004).
- **Confirming rerun**: `output/zsim.log` from the post-fix run shows no `MicroAllocator` error text and an `MMIO_MEASURE=1` write (Invoke() started) instead.
- **Remaining limitation**: The exact root cause within the guarded-local-static codegen path was not further isolated (e.g. by inspecting the generated guard-check assembly) given time constraints; the global-scope workaround is a completely standard C++ pattern and is confirmed to work, so further root-causing was not pursued.

## ISS-004: Full 20-case RTL vs. native TFLM comparison did not complete within session time

- **Symptoms**: After ISS-003's fix, the firmware correctly reaches `Invoke()` for case 0 (`MMIO_MEASURE=1` at RTL cycle 351185) but no `MMIO_MEASURE=2`, `MMIO_PREDICTED_CLASS`, or `MMIO_STATUS` write was observed within the simulation wall-clock time available in this session.
- **Reproduction**: Run `build/firmware/firmware.hex` on RTL via Animas with a large `+MAXCYCLES`; separately, a bounded run with `+MAXCYCLES=5000000` reached `SIM_TIMEOUT` still inside case 0's `Invoke()`.
- **Log location**: `output/zsim.log` (the `MMIO_MEASURE`/`SIM_TIMEOUT` lines).
- **Diagnosed cause**: Not a defect — a single `Invoke()` of this model (FULLY_CONNECTED 2048->32, then 32->4) requires at least 65,536 hardware multiply operations for the first layer alone; each multiply on this core's sequential shift-add multiplier takes ~33 cycles, and most surrounding instructions retire in ~7-11 cycles on this non-pipelined multicycle core. This genuinely puts a single `Invoke()` in the multi-million-RTL-cycle range. Compounding this, orchestrating a long-running Animas/Zenith simulation job through the available MCP tool interface in this session had its own real friction: `run_simulation` calls for long jobs returned a "timeout"/"headless" status to the calling tool after a bounded period (observed ranging ~30-300s) while the underlying simulation sometimes appeared to continue in an Animas backend process independent of the tool call's own lifecycle, and in other instances appeared to have stopped producing new output; the output file was also block-buffered, making live progress monitoring from the shell unreliable (file size/log content could appear frozen for tens of seconds at a time while separate evidence, such as the Animas backend process's own `/proc/<pid>/stat` CPU-time fields, confirmed it was still computing).

- **Resolution**: Not resolved within session time. The 20-case criterion is reported as incomplete (0/20 cases completed on RTL) rather than claimed complete.
- **Confirming rerun**: N/A — a continuation session with more wall-clock budget, or a faster/pipelined core (explicitly out of scope for this prompt), would be needed to complete this.

## ISS-005: `tb/soc_tb.sv` elaboration error on first real compile after this continuation's edits (`retired_count` used `retire_valid` before its declaration)

- **Reproduction**: This continuation's rewrite of `tb/soc_tb.sv` (adding `SIM_BANNER`, `HEARTBEAT`, and an always-on `retired_count`) placed the `retired_count` always_ff block (which reads `retire_valid`) near the top of the module, before `logic retire_valid;` was declared further down in the "DUT + memory model" section. - **Diagnosed cause**: Declaration-order bug introduced during this continuation's own editing, not a pre-existing defect. SystemVerilog does not forward-declare module-scope signals referenced inside `always_ff` blocks positioned textually earlier in the module.
- **Attempted fixes**: Moved the `retired_count` declaration and its always_ff block to immediately before its first use site (right before the existing `RETIRE` trace block, after `retire_valid` is declared from the `soc_top` port list).
- **Resolution**: Fixed. Confirmed by rerun: the next `run_simulation` call elaborated cleanly (only pre-existing, already-documented lint warnings; same warning set as recorded elsewhere in this project) and ran to completion for both a 10-cycle floor probe and a 200,000-cycle bounded benchmark (see `results/benchmark_throughput.json`).

## ISS-008: `scripts/compare_results.py` always exited 0 regardless of actual match count

- **Symptoms**: Re-running `compare_results.py` against the real 8/20 historical partial-match data printed a correct-looking summary (`matched=8 mismatched=0 incomplete=0 not_run=12 ...`) but the process exit code was 0 either way -- the same as a genuine 20/20 pass.
- **Diagnosed cause**: The script computed and wrote all the right numbers into its output JSON and printed a human-readable summary, but never translated that verdict into `sys.exit(...)` -- it fell through to the implicit exit 0 at the end of `main()` regardless of `matched_count`.
- **Resolution**: Added explicit exit-code logic: exit 3 for provenance/duplicate conflicts, exit 1 for any mismatch, exit 2 for incomplete coverage (matched != n_cases), exit 0 only when `matched_count == n_cases`. Also added atomic (`.tmp` + `rename`) writes to this script and to `scripts/run_rtl_test.py`, so a disk-quota failure mid-write (see ISS-007) cannot leave a truncated result file in place of a valid one.
- **Confirming rerun**: Re-ran against the real 8/20 historical data: now correctly prints `EXIT 2: incomplete -- 8/20 matched, 0 incomplete, 12 not run` and exits with code 2 (previously always 0). Re-ran against the final `full20_final_001` run record: prints `EXIT 0: all 20/20 cases matched` and exits 0.
- **Remaining limitation**: None -- a caller (e.g. a CI-style gate) can now trust this script's exit code alone, which was the point of the fix.

## ISS-009: `waveform_mode="off"` insufficiency (ISS-007) and the Animas `run_simulation` wall-clock cap, both resolved by bypassing the MCP daemon

- **Symptoms**: Beyond the quota exhaustion already documented in ISS-007, a later long run was reported to have ended with "Wall-clock cap (30 min) reached -- simulation cancelled." It was unclear whether this was a Zenith-level limit, an Animas-backend limit, or an artifact of a different, unrelated run.
- **Investigation**: Inspected the exact installed Zenith binary's own `--help` output directly (`flatpak run --branch=1.0.2 --command=zenith com.mifraltech.animaseda --help`): Zenith itself has `--end` (simulated time, not wall-clock), `--max-delta`, and `--max-handoffs`, but **no wall-clock-seconds flag at all**. This established that any such cap must come from the Animas backend's own handling of the `run_simulation` tool call (its `timeout_seconds` parameter), not from the simulator.
- **Resolution**: Rather than tuning `timeout_seconds` (which still leaves the waveform-generation risk from ISS-007 unresolved, and keeps the run dependent on an Animas-backend-mediated job), validated and switched to a standalone invocation of the exact same installed Zenith binary (`flatpak run --branch=1.0.2 --command=zenith com.mifraltech.animaseda ...`, backgrounded as a plain host process, output redirected directly to a file under `results/rtl_logs/`). This has no tool-call-level timeout of any kind, and omitting `--zwdb` entirely (confirmed via two pilot runs: zero `.zwdb` files created, no such file descriptor open by the worker process) solves the waveform problem in the same step. See `docs/decisions.md` D-009.
- **Confirming rerun**: The final run `full20_final_001` used this method for the full ~96-minute, 142,937,769-cycle run, completing cleanly (`$finish exit code 0`) with no quota issue and no waveform file produced.
- **Remaining limitation**: The Animas MCP `run_simulation` path (with `waveform_mode="off"`) remains available and is still useful for shorter/interactive work where its richer tool integration (live diagnostics, waveform inspection when actually wanted) is worth the tradeoff; it was simply not the path used for the final long run.
