## D-002: Use a hand-written Python ISA reference model instead of Spike

- **Question**: What serves as the independent ISA reference for comparing retired-instruction traces against the RV32IM core (prompt Section 6)?
- **Alternatives**: (a) Spike (preinstalled at `/edatools/opensrc/spike/1.1.1-dev`); (b) Sail; (c) a from-scratch Python functional model, per the prompt's explicit contingency.
- **Selected**: (c), a from-scratch Python RV32IM functional model (`scripts/isa_reference_model.py`), built directly from the RISC-V ISA specification without reading or reusing any DUT RTL logic.
- **Rationale**: Spike is present but cannot run on this host — it is linked against `libboost_regex.so.1.66.0` / `libboost_system.so.1.66.0`, and no compatible Boost 1.66 build exists anywhere on the system (see docs/issues.md ISS-001). Sail was not found on the host and would require a build from source, which is a worse use of the implementation deadline than writing a compact reference interpreter for a 2-extension (I+M), no-privilege-mode subset. The prompt explicitly sanctions this fallback: "If unavailable within the deadline, implement a separate functional verification model from the specification, without reusing DUT logic, and record that limitation."
- **Evidence**: docs/issues.md ISS-001 (ldd output, missing library search).
- **Consequences**: Verification evidence is against an independently authored second implementation of the ISA, not against an externally maintained, widely trusted reference such as Spike/Sail. This is weaker evidence than a Spike comparison and is reported as such in docs/handoff/limitations_and_open_questions.md.
- **Status**: active.

## D-004: Library shim (`LD_LIBRARY_PATH`) to repair the RISC-V GNU toolchain's broken `cc1`/`cc1plus`

- **Question**: `riscv64-unknown-elf-gcc`/`g++` (16.1.0, from the `riscv-gnu-toolchain/elf-multilib/2026.07.15-elf` module) failed to run at all: `cc1`/`cc1plus` reported `libmpfr.so.4: cannot open shared object file`, and after supplying that, `libgmp.so.7: cannot open shared object file`. The host's system libraries are newer (`libmpfr.so.6`, `libgmp.so.10`) and not ABI-compatible drop-ins.
- **Alternatives**: (a) treat the toolchain as unusable and look for another RV32 toolchain/build one from source; (b) locate the exact missing SONAMEs elsewhere on the host and supply them via `LD_LIBRARY_PATH` without touching the toolchain installation itself.
- **Selected**: (b). Exact-SONAME copies of `libmpfr.so.4` and `libgmp.so.7` exist under the Xilinx Vivado 2025.2 installation tree (`/edatools/amd/xilinx-vivado/2025.2/...`), bundled there for Vivado's own tools. Symlinking just these two specific files into a small, isolated shim directory (not adding the entire Vivado `lib` directory to `LD_LIBRARY_PATH`, which was tried first and broke `g++` itself by shadowing `libstdc++.so.6` with an older, incompatible build) resolved both missing-library errors.
- **Rationale**: Building riscv-gnu-toolchain from source was explicitly discouraged by the prompt ("Avoid a full toolchain source build when a suitable local or prebuilt alternative exists"); a prebuilt, correctly-targeted toolchain already exists on this host and only has a narrow, repairable linkage problem.
- **Evidence**: see docs/development_log.jsonl E014; verified by compiling and linking a minimal freestanding RV32IM/ilp32 C++17 program to a valid ELF (`readelf -h`, `objdump -d` inspected).
- **Consequences**: Every build command for sw/ firmware must set `LD_LIBRARY_PATH` to include this shim directory (recorded in scripts/env.sh) in addition to loading the `riscv-gnu-toolchain/elf-multilib/2026.07.15-elf` module. This is a host environment workaround, not a toolchain or RTL design choice.
- **Status**: active.

## D-006: Quality target (quantized test macro-F1 >= 0.85) not met; proceed without further architecture search

- **Question**: Model A (hidden=16) and Model B (hidden=32), trained and quantized under the exact protocol in Section 4, reached quantized validation macro-F1 of 0.754 and 0.768 respectively, both below the 0.85 target. The prompt permits trying A then B and choosing between them by quantized validation performance only — it explicitly forbids an open-ended architecture search. What happens next?
- **Alternatives**: (a) keep tuning architecture/hyperparameters until 0.85 is reached; (b) accept Model B (higher quantized validation macro-F1: 0.768 vs 0.754), report the true quantized test macro-F1 (0.771), and continue the functional (processor + TFLM) demonstration with this model as specified.
- **Selected**: (b).
- **Rationale**: The prompt is explicit: "Do not launch an open-ended architecture search" and "If the target is not reached, preserve the actual result, explain the limitation, and continue the functional demonstration. Do not change the threshold, labels, or test data to claim success."
- **Evidence**: docs/experiments.jsonl RUN-train-quantize-001; results/ml_metrics.json.
- **Consequences**: The quality target (test macro-F1 >= 0.85) is an unmet, explicitly reported acceptance criterion. The 20-case RTL-vs-native-TFLM agreement criterion is a separate, independent acceptance criterion (bit-exact agreement between RTL and the native reference, not agreement with ground truth) and is not affected by this shortfall — Model B's real misclassifications are expected to reproduce identically on both RTL and the native reference.
- **Status**: active.

## D-007: Lightweight alternative RAM testbench model (tb/ram_model_lite.sv)

- **Question**: Profiling the long RTL functional run (RUN-firmware-rtl-001) showed Animas/Zenith simulating at only ~3,700 RTL cycles/sec. Is the testbench itself (not the core) a significant, avoidable source of per-cycle simulation overhead?
- **Investigation**: Inspected `rtl/rv32im_core.sv`'s FSM directly: it is strictly single-outstanding-request (`S_FETCH -> S_FETCH_WAIT -> S_DECODE -> S_EXECUTE -> ... -> S_WRITEBACK -> S_FETCH`, and likewise through `S_MEM_ADDR -> S_MEM_WAIT`) -- a new `mem_req` is never issued before the prior response has arrived; at least one extra state always separates a response from the next request. `tb/ram_model.sv`, however, ages a `MAXLAT=64`-deep shift-register pipeline (two 64-element arrays, `pend_valid`/`pend_rdata`) on **every** clock cycle, regardless of whether anything is pending -- roughly 126+ signal updates per cycle for a design that, given the verified property above, only ever needs to track 0 or 1 in-flight response at a time.
- **Alternatives**: (a) leave `ram_model.sv` as the only RAM model; (b) add a second, lightweight RAM model using a single pending-response flag + countdown counter instead of the 64-deep shift register, selectable at compile time, keeping the original available unchanged.
- **Selected**: (b). `tb/ram_model_lite.sv` implements the same external interface, the same `+MEMFILE=`/`+FIXEDLAT=`/`+READYWAIT=`/`+RANDWAIT=` plusargs, the same byte-write-strobe semantics, and was derived to produce bit-identical `req_ready`/`resp_valid`/`resp_rdata` timing to `ram_model.sv` (worked through algebraically: both models assert `resp_valid` exactly `lat+1` cycles after the cycle a request is accepted, where `lat = FIXEDLAT + extra` and `extra` is drawn from the same single `$urandom_range(rand_wait_max, 0)` call per accepted request in both models, so a fixed `--seed` produces the same draw sequence in both). `tb/soc_tb.sv` selects between them at compile time via `` `define RAM_LITE `` (default: the original `ram_model.sv`, so existing behavior is unchanged unless explicitly opted into the lite model).
- **Rationale**: Section 5 of this continuation's instructions explicitly calls for verifying the single-outstanding-request property first and, if confirmed, building exactly this kind of lightweight alternative while keeping the original for comparison -- this follows that guidance directly rather than jumping straight to a core redesign.
- **Evidence**: `rtl/rv32im_core.sv` FSM (manual inspection, cited above); `tb/ram_model_lite.sv`'s header comment contains the same analysis. A runtime `$error` check in the lite model flags (without corrupting state) the case where a new request is accepted while a response is still pending -- i.e. if this model is ever reused with a core that does NOT have the single-outstanding property, misuse is reported loudly rather than silently producing wrong timing.
- **Consequences**: Before being relied on for real results, the lite model must be validated against the original via short deterministic transaction tests and the existing processor test suite (directed tests + the 1100-instruction random comparison), under default timing, nonzero `READYWAIT`, and `RANDWAIT` with a fixed seed -- see docs/experiments.jsonl for the validation run once performed. Until that validation is recorded, results produced with `` `define RAM_LITE `` must be treated as unverified, not yet as a validated faster path.
- **Status**: **VALIDATED (2026-11-08)**, once Animas MCP connectivity was restored (see docs/issues.md ISS-002 recovery note). Validation performed:
  1. **Random-instruction program** (1100 instructions, `build/random_program/random.hex`), RETIRE-traced (`+TRACE=1`) end to end, compared byte-for-byte between `ram_model` and `ram_model_lite`:
     - Default timing (`FIXEDLAT=2 READYWAIT=0 RANDWAIT=0`): exact match, 1100/1100 RETIRE lines identical (pc/instr/rd_we/rd_addr/rd_wdata/cycle), `diff` exit code 0.
     - Injected backpressure + randomized latency (`FIXEDLAT=3 READYWAIT=2 RANDWAIT=5`, `--seed 4242`), with BOTH runs confirmed via their own `command` field to be literal, matched headless-subprocess invocations (ruling out the `--seed`-dropping daemon-translation issue below as a confound): exact match, 1100/1100 lines identical including cycle numbers, `diff` exit code 0. An earlier attempt at this same comparison appeared to show growing, oscillating-sign cycle discrepancies (up to ~11 cycles) — root-caused to one of the two runs going through `ui_remote_control` (daemon) mode, which silently dropped `--seed` (not in the documented cflag allow-list for daemon translation; see `docs/animas_capabilities.md`), giving the two runs genuinely different `$urandom` streams. Once both runs were confirmed headless with the literal seed on the command line, the discrepancy vanished completely.
  2. **Full 9-test directed regression** (`tb/directed/test_001`..`test_009`), run individually under `ram_model_lite` (via the `+define+RAM_LITE` cflag, confirmed by each run's own `ram=lite` / `[ram_model_lite] loading...` banner): all 9 PASS, with the same cycle counts observed earlier for several tests under the original model (e.g. test_002: cycle=442/449 both models; test_004: cycle=69 both models). test_009 (compiled C program) needed `+MAXCYCLES=500000` instead of the default 50,000 (a program-size issue, unrelated to the RAM model) but then passed.
  3. **Benchmark** (Section 5's explicit requirement): the firmware's first 200,000 RTL cycles, run twice under each RAM model. `ram_model_lite`: 20s, 20s (Zenith's own `[zenith] simulated for 00:00:20` line, headless mode both times). `ram_model` (original): 28.832s, 28.655s (animas.log `"Simulation started"`/`"Simulation done"` timestamps, `ui_remote_control` mode both times). **Observed speedup: ~30% wall-clock reduction (~1.43x)** for this workload -- a real, reproducible improvement, though the two measurement methodologies differ (Zenith-internal timer vs. daemon start/done), so the magnitude should be treated as approximate, not a precisely isolated single-variable measurement. See `results/benchmark_throughput.json`.
  4. **Procedural finding, recorded for future reference**: `set_sim_options`'s structured `defines` parameter is unreliable across execution modes -- it worked when a run happened to go through `ui_remote_control` but was silently dropped when a run happened to go through `headless`, and vice versa for `+define+RAM_LITE` passed as a raw `cflags` string in one specific observed case. The only robust way found to guarantee the intended RAM model is selected is to pass `+define+RAM_LITE` as a `cflags` entry AND verify the resulting log's own `ram=lite`/`ram=full` banner field after every run, rather than trusting either input mechanism blindly.
- **Consequence of validation**: `tb/ram_model_lite.sv` is adopted as the RAM model for the long-running case-0/20-case TFLM inference work in this continuation, given the confirmed timing-equivalence and the real (if modest) throughput improvement. The original `ram_model.sv` remains available and registered in the project for any future comparison.

## D-008: Compile-time `CASE_START`/`CASE_COUNT` firmware range selection, and real `scripts/run_rtl_test.py`/`scripts/compare_results.py`

- **Question**: Section 6/8 of this continuation require "a controlled way to run a selected comparison case or range" and a real aggregate checker, noting that source comments already referenced `scripts/compare_results.py`/`scripts/run_rtl_test.py` by name despite neither existing. How should case-range selection and result checking be implemented without embedding ground truth in the firmware or silently merging inconsistent evidence?
- **Alternatives**: (a) leave the firmware running all 20 cases unconditionally per invocation, accepting that any tool-call/wall-clock limit loses all progress on a timeout; (b) add compile-time `CASE_START`/`CASE_COUNT` defines (static_assert-validated, global case-ID numbering preserved in MMIO_CASE_ID, no ground truth embedded) so a run can cover one case or a sub-range, paired with real checker scripts that can merge multiple partial-run records.
- **Selected**: (b). `sw/app/main_firmware.cc` now loops `for (int i = CASE_START; i < CASE_START + CASE_COUNT; i++)`, defaulting to `CASE_START=0, CASE_COUNT=N_COMPARISON_CASES` (unchanged behavior with no `-D` flags). `scripts/build_firmware.sh` compiles only `main_firmware.cc` per config (all other TFLM/platform objects are built once into a shared cache and reused across configs), writes a config-tagged ELF/hex/map/disassembly under `build/firmware/configs/<tag>/`, and records `firmware_config.json` (case_start, case_count_requested, elf_sha256, build timestamp). `scripts/run_rtl_test.py` parses `tb/soc_tb.sv`'s structured log markers into a provenance-tagged per-run JSON record (distinguishing `completed_status_ok` / `error_halt` / `sim_timeout` / `truncated_log_no_terminal_marker` -- the last one specifically to avoid conflating "the MCP tool call returned" with "the simulator actually stopped", per Section 3). `scripts/compare_results.py` merges one or more such run records against `results/native_reference/output.jsonl` and `results/comparison_manifest.json`, requiring exact agreement on all 4 scores + predicted class for a `MATCH`, and explicitly rejecting missing cases (`NOT_RUN`), cases with conflicting results from different runs (`DUPLICATE_CONFLICT`), and whole runs with unverifiable model/ELF provenance (`PROVENANCE_CONFLICT`).
- **Rationale**: This is the literal, explicit requirement set out in Sections 6 and 8 of this continuation's instructions, including the explicit warning not to claim a checker exists merely because a comment names it, and the explicit requirement not to embed expected scores/labels in the firmware.
- **Evidence**: default-config rebuild reproduces the exact previously-recorded ELF SHA-256 (`622d1816...`); a deliberately out-of-range `CASE_START=18 CASE_COUNT=5` request fails at compile time via `static_assert`; both checker scripts were self-tested against synthetic logs covering match/not-run/duplicate-conflict/provenance-conflict before being trusted on real data (see `docs/experiments.jsonl` RUN-firmware-build-002, RUN-checker-scripts-validation-001).
- **Consequences**: Any future RTL run must pass `--model-sha256` and either `--elf` or `--firmware-config` to `run_rtl_test.py`, or its output will be rejected by `compare_results.py` as a provenance conflict (by design -- an unverifiable run must not silently count toward the 20-case result). The legacy fixed path `build/firmware/firmware.elf` is still written for the default `case_full` config only, for compatibility with any existing tooling that references it directly.
- **Status**: active; superseded-as-written -- `compare_results.py` was later found to always exit 0 regardless of actual match count (a reporting bug fixed in the 2026-11-08 finalization session) and both checker scripts have since been exercised against real Animas run data (the final accepted run `full20_final_001`), not just synthetic logs. See D-009/D-010 below.

## D-009: Standalone Zenith invocation (bypassing the Animas MCP daemon) for the final run

- **Question**: Two problems blocked a trustworthy complete 20-case run via the normal `mcp__animas__run_simulation` path: (1) `waveform_mode="off"` was found not to reliably prevent large ZWDB files from being written (ISS-007), risking another disk-quota failure during a ~90-minute run; (2) a reported "wall-clock cap (30 min)" turned out to be an Animas-backend-level `timeout_seconds` on the tool call itself, not a Zenith simulator limit (confirmed via the installed binary's own `--help`: no wall-clock-seconds flag exists in Zenith). How should a single long, trustworthy, waveform-free run be launched?
- **Alternatives**: (a) keep using `run_simulation` with `waveform_mode="off"` and a large `timeout_seconds`, accepting the unverified risk that a ZWDB still gets written and that some other backend-side cap might still apply; (b) invoke the exact same installed Zenith binary standalone (`flatpak run --branch=1.0.2 --command=zenith com.mifraltech.animaseda ...`), backgrounded as a plain host process, entirely bypassing the Animas daemon.
- **Selected**: (b). Validated first via two pilot runs: confirmed zero waveform output (no `--zwdb` argument at all; `/proc/<pid>/fd` showed no ZWDB file handle) and functionally identical results (3 regression tests matching previously-recorded cycle counts exactly, and `ram=lite`/`trace=0` correctly reflected in the run's own `SIM_BANNER`).
- **Rationale**: A backgrounded host process has no tool-call-level timeout at all, and omitting `--zwdb` is a directly observable (not merely requested) way to produce zero waveform output -- both problems are solved by the same change, without touching installed Animas/Zenith source, binaries, or global settings (only a documented per-run invocation style).
- **Evidence**: `results/final_run_evidence/full20_final_001_fingerprints.json` (`launch_method` field); the final run's own log shows zero `.zwdb` files created (`find . -name '*.zwdb'` before/after comparison) and the worker's only open file descriptors are `/dev/null` and the redirected log file (`/proc/<pid>/fd` inspected directly during the run).
- **Consequences**: The portal-mounted path (`/run/flatpak/doc/<id>/<project>/...`), not the host path, must be used for every file argument (`+MEMFILE=`, source files) -- the sandboxed process cannot resolve host paths directly (confirmed via an initial failed pilot: `[ZEN-0511] cannot open source file`). The Animas MCP tool path remains available and documented as an alternative for shorter/interactive work.
- **Status**: active; used for the final accepted run.

## D-010: `scripts/check_final_run.py` -- a new, stricter single-run acceptance checker, distinct from `compare_results.py`

- **Question**: `compare_results.py` is designed to merge potentially multiple partial run records and was found to always exit 0 regardless of actual match count (a reporting bug: it printed a correct-looking summary but never translated it into the process exit code). Separately, Section 6/8 of the finalization instructions require a strict acceptance gate for exactly one complete run that fails loudly on any structural ambiguity (missing event, case-id sequence gap, non-monotonic cycles, duplicate banner) rather than silently producing a plausible-looking partial report.
- **Alternatives**: (a) only fix `compare_results.py`'s exit code and reuse it for final acceptance too; (b) fix `compare_results.py` for its existing aggregation role, and write a new, separate, much stricter checker purpose-built to answer exactly one question for exactly one log file.
- **Selected**: (b). `compare_results.py` was fixed (exit 0 only on full n/n match; exit 1/2/3 for mismatch/incomplete/provenance problems respectively) and kept for its aggregation role. `scripts/check_final_run.py` was added: it refuses to pair a case's Invoke-end with any later case's prediction if the immediately-expected prediction event is missing (exit 2), rejects non-monotonic cycle counts, requires exactly one correctly-ordered final status marker, and only then compares all 20 cases' scores/class against the native oracle exactly.
- **Rationale**: Keeping the two scripts separate avoids conflating "the best aggregate picture across possibly-multiple historical runs" (compare_results.py's job) with "is this one specific run, by itself, a fully valid final result" (check_final_run.py's job) -- a later reader should not have to guess which guarantee a passing exit code represents.
- **Evidence**: Both scripts were validated against synthetic good/malformed logs (good, case-id gap, mismatch, dual-banner, err-halt cases) before being trusted on real data; `compare_results.py` was then re-run against the real historical 8/20 partial data and correctly produced exit code 2 (`EXIT 2: incomplete -- 8/20 matched...`); `check_final_run.py` was then run against the real final log `full20_final_001` and produced exit code 0 (`ACCEPTED: ALL 20/20 CASES MATCH`).
- **Consequences**: `results/final_run_evidence/full20_final_001_check_report.json`'s `"accepted": true` / `"exit_code": 0` is the authoritative pass/fail verdict for the final result; `results/rtl_comparison.json` is regenerated from the single `full20_final_001` run record only (not merged with the historical 7/20 or 8/20 partial evidence, which remains separately preserved in `results/rtl_comparison_partial_per_case_runs.json`).
- **Status**: active; this is the final, accepted result.
